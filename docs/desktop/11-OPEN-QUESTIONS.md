## A · 功能范围（按"广而不深"定调）

> **定位已定**（DEC-027）：**单兵全能工具**。一个人要覆盖告警分诊、漏洞评估、事件调查、取证分析、合规检查、报告输出——**每项不需平台级深度，但都得能干**。
>
> **取向定调：广而不深。** 据此四件事的方向已定，具体取值等 **M1.5 自用验证**的真实反馈来收敛：

| 问题 | 定调 | 何时收敛 |
|---|---|---|
| 数据源 | 先接**通用性最强的两三个**，不深集成某一家 | M1.5 反馈 |
| 合规工作台 | **做轻**：知识问答 + 差距分析 + 报告。控制项状态台账留到有人要 | M1.5 反馈 |
| 产出物 | 先 **markdown**。模板系统等有人抱怨了再说 | M1.5 反馈 |
| 工作项数据模型 | 依赖上面三条 | M3 |

**仍然有效的结构判断**（不受定位变化影响）：

- 两种工作结构确实不同：**执行流驱动**（调查，执行→观察循环）vs **工作项驱动**（决策，多个并行判断，每项"多源找信息 → 判断 → 产出交付物"）。单兵两种都会遇到，界面要两者都能承载。
- 布局三栏 + 状态栏，共用 `ui-shared` 骨架。
- **没有"审批队列"模块**——别人提交待我决定的审批只有 connected 才有。单兵只有 Plan Mode 式的执行前确认，那是弹窗不是列表。

## B · ~~advisory 的桌面端理由较弱~~ → **已解决**

**结论**（DEC-027）：桌面端的价值**只对"没有服务端的人"成立**，而单兵就是这批人。

对已部署 CyberGuard 的客户，桌面端 advisory 的增量价值接近于零——Web 端 21 个 Tab 功能不减，打开浏览器就有全部审批、GRC、审计。"不用部署"归零、"数据不出本机"不成立（数据本就在服务端）、"本地 MCP"服务端网络位置往往更好。

**所以不是"advisory 该做桌面还是 Web"，而是"目标客户有没有服务端"。** 定位为单兵后，这个问题消失。

## C · MCP 连接器覆盖度

> **进程生命周期已全部决完** —— 见 `../superpowers/specs/2026-07-29-mcp-connector-lifecycle-design.md`。

## G · 「Agent vs Agent」是否进入核心交互

工作区目录名是 `agent-vs-agent`，服务端已有 Group Chat 轮转 + 语义共识。桌面单兵产品是否把 **多专家对辩 / 交叉审查** 做成默认路径，还是保持「单 agent + 工具」为主、对辩为可选？

| 选项 | 含义 | 风险 |
|---|---|---|
| 主路径 | 告警分诊等场景默认拉 2+ 视角互相质疑再出报告 | 权限主体变多（INV-22 节点不做 spawn 时只能同会话内角色切换）；延迟与 token 成本上升 |
| 辅助 | 用户显式开「多视角」时才启用 | 与仓库叙事弱相关，但更贴单兵默认 |
| 不做 | 桌面端不移植群聊对辩 | 最简单；与目录名脱节，可改名 |

**何时收敛**：M1.5 黄金路径跑完后（见 `12-M1.5-GOLDEN-PATH.md`）。在此之前**不为对辩单独抽内核**。
