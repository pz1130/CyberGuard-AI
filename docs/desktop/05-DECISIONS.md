# 05 · 决策记录

状态：活文档 · 追加不修改

每条记录已定的决策、当时的备选、以及为什么。**目的是避免重复讨论已经想清楚的事。**
决策要推翻时不删除原条目，追加一条新记录说明触发原因。

## 稳定性总览

| 标记 | 含义 | 可否作为定论 |
|---|---|---|
| 🔒 **稳定** | 提出后从未改动，且有多条独立理由支撑，经过多轮不同角度冲击 | **可以** |
| ⚖️ **较稳** | 改过一次或新定不久，但改后的理由比改前硬（多有具体失败案例支撑） | 基本可以，再变可能性低 |
| 🚧 **未定** | 明确会随产品决策变化，或对应文档尚未按新方向重写 | **不要**，等冻结 |
| ⛔ **已被取代** | 结论作废，保留原论证作为记录 | 不要，看取代它的那条 |

**变更约定**：读到可能推翻已定结论的新材料时，**先说明"这会推翻 X，要不要为此改"，而不是直接改完再通知**。改与不改由产品决定，代价可见。

**未冻结事项一律登记在 `11-OPEN-QUESTIONS.md`**（含 advisory 功能范围、09 协议细节、Skill 七个缺口、记忆层遗留、工程量待估），每条注明阻塞的里程碑。本文只记已定的结论。

## 🔒 DEC-001 · 单仓库，不拆新仓库

**决策**：桌面端进现有 `cyberguard` 仓库（`apps/desktop/`），共享包放 `packages/`。

**备选**：独立仓库 + 私有 registry 发布 `agent-core` 与 `ui-shared`。

**理由**：两个共享包跨仓库版本协调，对小团队是持续摩擦。Gateway 协议改动会同时触及服务端与节点，单仓库可原子提交。现有基线测试留在原地当安全网。将来要拆很容易，合并很难。

**代价**：桌面端开发者要拉一个较大的 Python 仓库。可接受——发布产物不含服务端代码。

---

## 🔒 DEC-002 · 桌面壳选 Electron，不选 Tauri

**决策**：Electron + electron-builder。

**理由**：
1. 需管理 Python sidecar 生命周期与 MCP STDIO 子进程——Electron 的 Node 侧几十行 JS，Tauri 需写 Rust sidecar，调试链路长。
2. 现有 UI 用 Tailwind v4（依赖 `@property` / `oklch`），Tauri 用系统 WebView，旧版 WebKitGTK 有兼容风险；Electron 自带 Chromium 无此问题。
3. 体积劣势被稀释——反正要打包整个 Python 运行时，安装包本就在几百 MB 量级。

**代价**：Chromium CVE 需跟进发版。接受。

---

## 🔒 DEC-003 · 壳 ↔ sidecar 走 stdin/stdout JSONL，不用 localhost HTTP

**决策**：JSONL over stdin/stdout（参照 pi 的 RPC 模式）。

**理由**：不开端口意味着同机其他进程无法连接，"随机 token 鉴权是否足够"这个问题从存在性上消失。对一个跑在有域凭据的员工终端上、能执行 shell 的产品，这是实质性差别。

**连带收益**：sidecar 不需要 FastAPI / uvicorn，依赖显著变薄，打包更容易。

---

## 🔒 DEC-004 · 首发 macOS，Windows / Linux 推迟二期

**决策**：本期只做 macOS。

**理由**：macOS 沙箱摩擦最小（单次 `sandbox-exec` + `.sbpl`，系统版本单一），能最快验证与平台无关的架构主体（RPC 通道、Gateway 接入、Plan Mode、UI）。

**已知风险**：企业 SOC 终端主体通常是 Windows，而 Windows 是隔离能力最弱的平台。二期若发现受限令牌 + ACL + Job Object 达不到可接受水平，Windows 节点定义可能收窄为"只做只读证据采集"。

**这是主动接受的风险，不是遗漏。** 缓解见 INV-15；重新评估触发条件见 `03-ROADMAP.md` 二期章节。

**约束**：在支线 W 有结论前，`sandbox_mode` 权限模型不作为对客户的正式能力承诺发布——错位成真时代价不是改代码，是改承诺。

## ⛔ DEC-005 · 复用现有 Gateway 协议，不另设计节点协议

> **已被 DEC-020 部分修正**：复用鉴权与任务模型的判断仍然成立，但"服务端主体零改动"不成立。桌面协议为 `desktop.v1`，权威字段见 `09-GATEWAY-PROTOCOL.md`，与 OpenClaw 最小协议并存不混用。

**决策**：新增 `backend_type = "desktop"`，复用 `poll` / `report` / `heartbeat` / `manifest` / `execute-tool` 与 `X-Api-Key` 鉴权。

**理由**：协议已存在且被 OpenClaw 节点验证过（`master.py::_routable` 已有对无 `endpoint_url` 后端的处理）。`AgentConfig` 的治理字段齐备，无需新建表。

**需扩展**：`report` 扩为结构化上报（当前只有 `{message_id, result: str}`，节点执行发生在服务端看不见的地方，审计链会断）；`heartbeat` 扩为双向控制通道（当前纯上行，导致 `kill_switch_enabled` 对已下发任务实际失效）。

## 🔒 DEC-006 · 复用服务端 agent 内核，不在节点侧重写

**决策**：抽 `packages/agent-core`，服务端与节点共用。

**理由**：`_run_loop` 里的循环守卫参数指纹归一化（`sort_keys=True`）、预算耗尽时撤工具而非报错、反思器两次纠偏上限、压缩时丢弃孤儿 tool 消息——每条背后都是一次线上问题。这些是**最难第二次写对**的部分。重写等于归零，且不知道漏了哪几条，只能靠用户帮忙发现。

**方法**：端口化而非重写。现有三个 adapter 注释已写明 "Mockable from tests via monkeypatch"，本就是雏形。

## ⛔ DEC-007 · ~~Episodic 经验库留服务端，节点不建本地向量库~~ → **已被 DEC-022 反转**

> **本条结论已作废。** standalone 形态下没有服务端可查，不建本地库等于没有经验积累。
> 新结论：**standalone 建本地经验库**；connected 后本地库仍在（个人经验），叠加服务端共享库（组织经验）。
> 本地经验上传服务端必须**可选、逐条显式确认、且过脱敏**。
> 下文保留原始论证——"跨人共享是结构性优势"这一点仍然成立，只是它属于 connected 的价值，不能成为 standalone 缺失经验能力的理由。

**决策**：节点经 gateway 查服务端；本地只允许"个人偏好"层。

**理由**：分析师 A 摸索出的打法应让 B 直接召回。这是相对 pi（无长期记忆）/ codex（锁在 `~/.codex`）/ grok-build（锁在个人 workspace）这类单机 CLI 工具的**结构性优势**。主动下放等于放弃差异化。

## 🔒 DEC-008 · PyInstaller onedir，不用 onefile

**决策**：onedir。

**理由**：onefile 每次启动解压到临时目录，与 macOS Hardened Runtime 冲突，且该行为在 Windows 上杀软误报率极高。onedir 目录可直接签名，启动更快。

## ⚖️ DEC-009 · 首版不装特权守护进程，抓包走服务端代执行

**决策**：`/dev/bpf*` 需要的抓包类工具标为 `governed`，走 `/gateway/execute-tool`。

**备选**：随包提供特权辅助工具（`SMJobBless` / launchd daemon），如 Wireshark 的 ChmodBPF。

**理由**：在客户终端安装特权守护进程会显著抬高安全评审门槛，不值得在 M1 阶段付这个成本。二期视客户需求再评估。

## 🔒 DEC-010 · 桌面端是单工作台，不搬 21 个 Tab

**决策**：单工作台布局（会话树 / 对话执行流 / 上下文面板 + 状态栏）。

**理由**：单兵在桌面端做的是**一件连续的工作**（看态势 → 判断 → 下场查 → 出结论），不是在多个管理模块间跳转。配置管理、治理审计、用户权限属于组织级操作，留 Web 端。搬全部 Tab 会造成两套后台并存、维护翻倍、且大部分在单机语境下无意义。

> 早期理由写的是"分析师只做调查这一件事"——按 DEC-027 的单兵全能定位，他两件事都做，但**仍然是一条连续链路**，结论不变。

## 🔒 DEC-011 · 不重写服务端

**决策**：服务端保持增量演进，只做 `agent-core` 抽取这一处结构性重构。

**理由**：基线测试、21 份带日期的设计文档、六周 362 次提交、分层清晰、失败路径普遍 best-effort 降级。已发现的问题（重复压缩实现、`messages_json` 并发、skills 全文注入、episode 无生命周期、关键词驱动控制流）**全部是局部的**，没有一条是动一处塌一片的架构腐烂。

重写会丢掉沉淀在代码里的决策——那些才是真正值钱的部分，而不是代码本身。

## ⚖️ DEC-012 · 节点不做子 agent spawn，并行止于同上下文工具并行

**决策**：桌面节点是叶子执行者。并行能力止于 `_run_loop` 现有的同一轮多 tool_call `asyncio.gather` 分发；不引入 spawn。

**备选**：参照 grok-build 的 parallel subagents + worktree 隔离，在节点侧支持子 agent。

**理由**：子 agent 不只是多一个执行器，它是**一个新的权限主体**——要回答 `sandbox_mode` 从哪继承、能否派给更宽松的配置、嵌套多深、审计链如何串联。OpenClaw 的三个连续沙箱逃逸公告全部出在这一层，不是巧合（见 INV-21）。

编码 agent 可以用灵活性换效率，因为错误代价是"代码写错了，回滚"。安全场景的错误代价是"扫描包已发出""封禁已生效""凭据已被读取"。**每多一个权限主体，安全审计成本上一个台阶（P4）。**

并行调查多网段、同时解析多份证据的收益，绝大部分从同上下文工具并行即可获得，且不新增权限主体、不新增上下文、审计链保持单条。

**需要"专门的日志分析 agent"时怎么办**：由服务端派两个任务下来，编排权始终在服务端，权限由服务端一次性裁定。

**连带修正**：原二期候选中的"子 agent 工作区隔离"归入**服务端范畴**（服务端 fan-out 的隔离与限流，见 INV-23），不是节点特性。

## 🔒 DEC-013 · 不采用自动学习闭环，技能变更须人工批准

**决策**：agent 可以**提议**新技能（附来源 episode 与证据），进待审队列，人工批准后才进技能池。

**备选**：Hermes 的学习闭环——任务完成后自动创建 skill 文件并立即可用，`skill_manage` 工具允许 agent 中途 patch 自己的技能。

**理由**：agent 自己写技能、自己加载、自己执行，在安全产品里等于**自我提权加持久化后门**。一次成功的 prompt 注入可以留下一条永久生效的技能，之后每次相关任务都会自动加载它。

**保留的部分**：Hermes 的两个设计仍然采纳——
1. **skill 与 memory 的分工定义**：memory 存小的、持久的、应始终在上下文的事实；skill 存较长的、只在相关时加载的过程。见 `08-MEMORY.md`。
2. **progressive disclosure**：只暴露 skill 的轻量描述，任务匹配时才加载完整正文。

**关联**：INV-20（能力变更须人工批准，P3）。

## ⚖️ DEC-014 · 共享内核拆两层，并提供 headless 模式

**决策**：共享代码拆成 `packages/llm-router`（纯 Provider 抽象）与 `packages/agent-core`（循环 + 端口）两个包；sidecar 除 RPC 外提供 headless / JSON 入口。

**参照**：pi 的四层划分（`pi-ai` / `pi-agent-core` / `pi-coding-agent` / `pi-tui`），每层独立可用、UI 层对其余包零依赖。

**理由**：
1. 现有 `llm_router.py`（944 行）混了纯路由能力与 `parse_intent` / `generate_summary` / `build_chat_system_prompt` 这类业务语义方法。后者属产品层，桌面节点用不到。拆开后节点不拖入服务端业务逻辑。
2. headless 模式不是锦上添花——M2 的沙箱逃逸用例集用它跑比驱动 Electron GUI 容易一个数量级；自动化响应剧本与 CI 回归也依赖它。协议本就是 JSONL，成本极低。

**连带**：`packages/ui-shared` 同样约束为对 agent 概念零依赖（参照 pi-tui）。

**不采纳的部分**：pi 的扩展热重载（见 INV-26）、极简工具集哲学（治理层对企业产品是价值不是负担）。但"内建最小工具集不可被下发覆盖"这一半采纳，见 INV-27。

## ⚖️ DEC-015 · 用 Operations 抽象实现两级工具执行

**决策**：工具不直接调用系统 API，改为依赖最小接口（`ReadOperations` / `ExecOperations` / `EditOperations`），每个工具只声明所需方法。本地沙箱执行与 `governed` 服务端代执行**通过注入不同实现**来区分。

**备选**：维持现状——`_dispatch` 内 if/elif 分四路（MCP / kb_search / 搜索 / 工具池），各自写各自的执行逻辑。

**参照**：pi 的同名设计，其动机是测试 mock 与远程执行（SSH、容器）。

**理由**：
1. 同一份工具代码复用于两种执行位置，消除分支复制。
2. **INV-18（两级执行边界不得模糊）从"靠代码走查"升级为"靠类型系统保证"**——节点侧不注入本地 `ExecOperations`，`governed` 工具在类型层面就无法本地执行，不需要靠 review 发现旁路。
3. 沙箱实现成为 `ExecOperations` 的一种，与 INV-15（沙箱平台无关声明）天然契合。

**关联**：INV-18、INV-15、`03-ROADMAP.md` M0a 第 6 项。

## ⚖️ DEC-016 · 策略管线与审计事件分离

**决策**：两套独立机制。策略走五步管线（`prepare_arguments` → `validate_arguments` → `before_tool_call` → `execute` → `after_tool_call`），**有干预能力**；审计走四层事件流（agent / turn / message / tool_execution），**纯观察、不可否决不可修改、emit 必须 await**。

**背景**：本方案早期版本（INV-28 初稿）把两者合并为"四个统一钩子"，是错的。

**理由**：合并会导致二选一的坏结果——要么审计订阅者获得了修改结果的能力（审计可篡改，合规上不可接受），要么策略检查失去阻断能力（拦不住高危动作）。pi 的划分是对的：管线干预、事件观察。

**连带要求**：事件 emit 必须 await 且按订阅顺序——**审计落盘后才继续下一步**。fire-and-forget 的审计对安全产品是个洞：任务已经推进，审计可能从未写入。审计写入失败须中止当前 turn（与 INV-25 一致）。

**关联**：INV-28、INV-29。

## ⚖️ DEC-017 · 节点本地运行 Agent Loop，Provider 凭据不经 Gateway 下发

**决策**：桌面节点运行完整的 `agent-core` loop。服务端下发 Provider 的非敏感元数据、模型能力和授权策略；节点使用写入 macOS Keychain 的节点级凭据调用本机或企业内网 Provider。

默认 Profile 只允许本机或企业内网 Provider。云端 Provider 只能通过显式的 `approved_remote` Profile 启用，界面显示数据出网提示并写入审计。

**不选**：让服务端代理所有 LLM 调用。那会把本地证据重新带回服务端，和 INV-10、离线运行以及桌面节点的产品目的冲突。

**边界**：服务端仍是 Provider 配置、模型验证、能力探测和授权策略的中心；节点不接收服务端 Provider 表中的原始 API Key，也不把节点级密钥上传服务端。

**关联**：INV-01、INV-02、INV-10、`01-ARCHITECTURE.md`、`02-TECH-STACK.md`。

## ⛔ DEC-018 · ~~首版只支持无密钥本地 MCP STDIO~~ → **已被 DEC-022 修正**

> **standalone 下不成立。** advisory 模式的数据全靠 MCP 连外部系统——SIEM、云平台、漏扫、工单——**这些全都需要凭据**。
> 新结论：**standalone 必须支持带凭据 MCP**，凭据进 Keychain 独立 slot，每个 MCP server 只能访问自己的 slot，不得跨 server 读取。
> connected 下仍可由服务端策略收紧（L1），或改走集中代执行。
> 下文保留原始论证。

**决策**：首版本地 MCP 只允许服务端批准的 STDIO server，manifest 下发固定 command、args、版本/hash、超时和沙箱声明；不下发服务端保存的 MCP 环境变量或认证 token。

带凭据的 MCP、HTTP MCP 和需要中心网络的位置继续走 `governed` 服务端代执行。未来如需本地凭据，凭据必须进入独立的 Keychain credential slot，不得扩展为把服务端密钥复制到节点。

**关联**：INV-01、INV-18、INV-20、`09-GATEWAY-PROTOCOL.md`。

## ⛔ DEC-019 · Episodic memory 只读经 Gateway，写入仍由服务端完成

**决策**：节点通过 `POST /gateway/episodic/recall` 查询组织经验；节点不直连数据库、不建本地向量库、不缓存召回结果。任务完成后，节点只在 report 中提交摘要、工具摘要和 success 标记，由服务端蒸馏并写入 `agent_episodes`。

**理由**：保持唯一写入路径和组织级审计边界，避免离线节点把未经校验的经验污染共享库。

## 🚧 DEC-021 · M1 只做 Mock 执行，M2 是真实工具执行的安全闸门

> **闸门对象已按双模式细化（DEC-024）**：M2 是 **operator 模式**启用真实本地工具的闸门。
> **advisory 模式不执行本地工具，因此不受 M2 阻塞**，可在 M2 之前交付。

**决策**：M1 只验证 Electron、sidecar、JSONL RPC、本地会话、headless loop、fake Operations 和 mock LLM。M1 不执行真实宿主工具，不连接真实 Provider。

只有 M2 的 Seatbelt、凭据隔离、保护性元数据只读、TCC 提示、签名公证出口判据全部通过后，才启用真实本地工具；M3 Gateway 接入依赖 M2 通过。

**理由**：避免在沙箱完成前出现可执行真实 shell 的不安全中间态。

**关联**：INV-01、INV-03、INV-15、INV-25、`03-ROADMAP.md`。

## ⚖️ DEC-022 · standalone-first：两种运行态，单机必须自洽完整

**决策**：桌面端是**自洽的单机产品**，服务端连接是**可选增强**。

| 运行态 | 说明 |
|---|---|
| `standalone` | 默认。全部核心工作流本地完成，不依赖任何服务端 |
| `connected` | 检测到并配对 CyberGuard 服务端后，叠加组织级能力 |

**核心原则**：**standalone 必须自洽完整，connected 只做增强。** 如果 standalone 是残废的、必须连上服务端才好用，这个形态就退化成"服务端的卫星"了。

**背景**：本方案早期版本把桌面端定位为"服务端的执行卫星"，是从既有 OpenClaw Gateway 协议顺推出来的，与产品目标不符——目标用户（独立顾问、中小团队安全负责人、未部署平台的企业）大多没有 CyberGuard 服务端。

**连带反转**（原设计假设有服务端，standalone 下必须翻过来）：

1. **本地经验库必须建**（反转 DEC-007 / INV-11）。上传服务端须可选、逐条确认、过脱敏。
2. **带凭据 MCP 必须支持**（修正 DEC-018）。凭据进 Keychain 独立 slot，每个 server 只能访问自己的 slot。
3. **审批降级为本地确认**，但审计中必须标注 `approval_type: self`，不得与职责分离审批混同记录。
4. **审计降级为本地哈希链**（tamper-evident），可选外发 SIEM。**不得宣称等同 WORM。**
5. **`governed` 集中代执行在 standalone 下不存在**，需要中心凭据或中心网络位置的工具直接不可用。
6. **MCP 从附属功能升为核心价值来源**——advisory 模式的数据全靠它聚合外部系统。
7. **必须自带内置安全 SOP 技能集**。用户装上去面对空技能池等于产品未完成。

**`agent-core` 端口的实现要求随之变化**：每个端口都需要**两套完整实现**，不再是"服务端实现 + 委托给服务端的薄壳"。尤其 `VectorIndex` 单机侧需要真正的本地向量库。

**关联**：DEC-023、DEC-024、DEC-025、INV-11、INV-06、`07-FEATURE-MATRIX.md`。

## ⚖️ DEC-023 · 服务端的价值是合规与协作，不是功能

**决策**：connected 提供五条 standalone **原理上做不到**的能力，除此之外不制造依赖。

1. **职责分离** —— 批准者 ≠ 操作者。单机上任何方案都是自批自，这是拓扑决定的。
2. **不可篡改审计** —— 日志不在被审计者机器上。本地哈希链能证明"没被改过"，但操作者可整条删除重开。
3. **跨人共享** —— 经验、技能、知识、事件上下文。
4. **组织级视图** —— 合规态势、跨事件统计、团队覆盖率。
5. **强制策略** —— 中心下发形成可审计的受控状态。

另有三条属"能做但集中更划算"，非不可替代：凭据集中管理与轮换、服务端能到而节点到不了的网络位置、定时与长时任务。

**商业含义**：**服务端不是技术必需品，是合规与协作必需品。** 单人用户永远不需要它；一旦客户要过审计、多人协作、或向监管与董事会证明"AI 操作受控"，它立刻变成刚需。单机版卖生产力，服务端卖**可证明的合规性**。

**强制策略的三级取舍**：

| 级别 | 内容 | 取舍 |
|---|---|---|
| L1 · 收紧执行策略 | 禁用特定工具、限制最高沙箱模式、强制审批档位、限制 LLM 出网 | ✅ **支持**。方向只能收紧，取本地与服务端策略的**更严者**，服务端不得放宽超过用户本地设定 |
| L2 · 收走数据 | 要求全量会话上传 | ❌ **不做**。与 INV-10 冲突；把"可证明合规"做成"监控软件"会卖不动 |
| L3 · 远程控制 | kill switch、远程 abort | ✅ **支持**。安全产品的基本要求 |

**脱管必须可见，但判定责任在服务端**：用户随时可断开回到 standalone——**阻止不了，不要试**。节点侧显示脱管状态 + 本地审计留痕 + 能上报时上报；**服务端侧按心跳超时判定**。
> 早期版本写的是"断开前上报并留痕"，**物理断网时做不到**（拔网线、关机都没有上报机会）——依赖节点自觉的机制，对最该发现的那类脱管恰好失效。已修正。

**关联**：INV-10、DEC-022、`09-GATEWAY-PROTOCOL.md`。

## 🚧 DEC-024 · 双模式：advisory 与 operator

**决策**：按**能力性质**而非角色命名的两种工作模式。

| | `advisory` · 决策模式 | `operator` · 作业模式 |
|---|---|---|
| 典型用户 | CISO、安全管理层 | 安全工程师、分析师 |
| 工作面 | 审批、态势总览、合规、审计查询、报告生成 | 会话树、执行流、证据浏览器、Plan 审阅 |
| agent 能力 | 检索 / 聚合 / 生成 | 上述全部 **+ 本地工具执行** |
| 沙箱要求 | 无（不执行本地工具） | 全套 Seatbelt / TCC / 保护性元数据 |
| 主要威胁 | **呈现污染**、幻觉误导决策 | 工具乱执行、经证据目录的注入、提权 |

按能力命名而非角色，是因为"能否执行本地工具"才是两者唯一的**安全本质差异**；且中小企业里一个人常常两者都要。

**授权来源**：
- `connected` —— 服务端按 RBAC 角色与授权策略下发"本节点可进入哪些模式"，界面只能在已授权集合内切换。
- `standalone` —— 由用户自行选择。单机上用户本来就有 root，**关键是不要假装有约束**：界面不得把一个用户能自行关闭的开关呈现为安全边界。

**排期收益**：advisory 不执行本地工具，因此**不依赖 M2 沙箱**，可以先于 operator 交付。用模式把安全闸门与交付节奏解耦。

**关联**：INV-37、INV-38、DEC-021、`03-ROADMAP.md`。

## 🚧 DEC-025 · 连接协议方向反转：上报 + 订阅，不是派单

**决策**：`connected` 下节点是**主动方**，服务端是**策略与存证的提供方**。

**背景**：原 Gateway 协议继承自 OpenClaw，是"服务端派单"模型——服务端建任务 → 节点 poll 取走 → 执行 → 上报，因而有 `GatewayMessage` 的 `pending → delivered → running` 状态机。

standalone-first 之后，任务由用户在本地发起，服务端不再是发起方。**方向整个反过来。**

| 原协议要素 | 新形态 |
|---|---|
| `poll` 派单 + 任务状态机 | **基本不需要** |
| `manifest` 下发工具/技能 | 降为可选（standalone 自带内置集，连接后叠加组织下发） |
| `execute-tool` 代执行 | **保留但可选**——价值是"服务端能到而节点到不了的网络位置" |

新协议需要的是六件：注册配对、策略拉取（L1）、**审批上收**（本地确认升级为服务端审批队列）、审计事件上报、经验双向同步、控制通道（kill switch / 远程 abort）。

**连带收益**：M6 的服务端改动比原方案**更少**——不必重做任务状态机，主要是新增几个上报与订阅端点。

**关联**：DEC-005、DEC-020、DEC-023、`09-GATEWAY-PROTOCOL.md` 需按此方向重写。

## 🔒 DEC-026 · Developer ID 签名 + 公证，自建更新通道

**决策**：发给客户但**不上架 App Store**。走 Developer ID 签名 + notarization（无需 App Review），自行分发 dmg/pkg。

**不选**：
- 上架 App Store —— 需 App Review 且强制 App Sandbox，跑不了本地扫描工具。
- 完全不签名 —— 要教客户绕过 Gatekeeper。**一个安全产品这么干，第一印象很难挽回**；且企业终端策略往往直接拒绝未签名应用。

**前置条件**：付费 Apple Developer Program 账号。证书有效期与吊销纳入运维——证书过期将无法签发新版本。

**须主动披露**：公证会把二进制上传给 Apple。政府、军工、金融类客户可能有疑问，应在产品说明中主动写清（仅自动恶意代码扫描，不涉及源码），不要等被问。

**自建更新通道是安全要害，不是便利功能**：客户终端上装着持有域凭据、能跑扫描与 shell 的应用，更新源被劫持即等于向所有客户终端投递任意代码的能力——**教科书式供应链攻击，且目标恰好是安全团队的机器**。要求见 INV-39。

**关联**：INV-39、`10-DEV-SETUP.md`、`03-ROADMAP.md` M7。

## ⚖️ DEC-027 · 产品定位：单兵全能工具

**决策**：桌面端面向**没有服务端的单个安全从业者**——独立顾问、中小企业安全负责人、大企业里有 SIEM 有工单但没有平台的个人。一个人既看态势也下场查，**不分角色**。

**背景**：Web 端保留全部 21 个 Tab 功能不减（DEC-011、M0b 出口判据）。**对已部署 CyberGuard 的客户，桌面端 advisory 的增量价值接近于零**——他打开浏览器就有全部审批、GRC、审计。"不用部署"归零、"数据不出本机"不成立（数据本就在服务端）、"本地 MCP"服务端网络位置往往更好。剩下的只有"免登录 + 托盘常驻"，撑不起独立形态的开发成本。

**所以桌面端的价值只对"没有服务端的人"成立**——而这批人恰恰是单兵。

**连带调整**：

1. **双模式降级为能力档位**（取代 DEC-024）。不再是运行态级的强制隔离，而是新建会话时可选"只读咨询 / 完整作业"，**默认完整作业**。上下文隔离的实质改由 INV-39 的内容级标记承担。
2. **`connected` 降为按需**。单兵不会部署服务端，M6 从既定阶段改为"有企业客户再启动"。端口抽象已保证将来可加，但不占当前排期与心智。
3. **功能取向：广而不深**。一个单兵要覆盖告警分诊、漏洞评估、事件调查、取证分析、合规检查、报告输出——每项不需平台级深度，但都得能干。

**关联**：DEC-024（被取代）、DEC-028、INV-39（重定义）、`03-ROADMAP.md`、`07-FEATURE-MATRIX.md`。

## ⚖️ DEC-028 · 分出"自用验证版"，与可分发版两条线

**决策**：产品分两条线交付。

| 线 | 目标 | 砍掉什么 |
|---|---|---|
| **自用验证版** | **最快跑通一条真实的安全任务链路**，验证产品方向 | 签名公证、沙箱、静态加密、卸载清理、更新通道 |
| **可分发版** | 给客户装 | 全套安全工程，即现有文档所述 |

**理由**：目前**没有客户**。从 M0a-1 到 M7 是个相当大的工程，而其中沙箱、公证、加密、审计哈希链、卸载、更新通道**全是"给别人用"才需要的**。在有真实使用反馈前，这套投入未经验证。

**单兵全能工具最好的第一个用户就是开发者自己。** 先让自己（或身边的安全从业者）用起来，拿到真实反馈，再决定安全工程投多少。

**这不推翻任何不变量**，只把"何时必须满足"往后挪。INV 全部约束在可分发版仍然有效。

**自用版的硬约束**（否则会违反 INV-38）：

- **禁止分发**。构建产物标记为开发版。
- **启动时明示**「开发版本，未启用沙箱与静态加密，请勿处理真实敏感数据」。
- **不宣称任何安全属性** —— 不宣称就不算伪装，这是它能合法跳过安全工程的唯一理由。

**关联**：DEC-027、INV-38、`03-ROADMAP.md` M1.5。

## ⚖️ DEC-029 · 桌面端 i18n：自建极简 `t()`，回答语言跟随界面语言

**决策**：桌面端支持中英文切换，机制自建，不引入 i18n 库。

| 项 | 结论 |
|---|---|
| 机制 | `renderer/i18n/` 两份 JSON + `I18nProvider` + `t()`，复数与插值自己写（约 120 行） |
| 默认语言 | 跟随系统（`navigator.language`），中文兜底 |
| 持久化 | 与 `theme` / `font_size` 同路：localStorage 缓存 + sidecar `ui_prefs.json` 权威源 |
| 回答语言 | **跟随界面语言** —— 切 en 时经 `agent.run` 已有的 `system_prompt` 字段注入英文指令，协议零改动 |
| 历史数据 | **不翻**。已存 JSONL 的会话标题与事件文本保持原文——翻译历史记录等于篡改证据 |

**理由**：`webui/` 用的是 i18next，将来若做 `ui-shared` 合流本可零摩擦。但用户确认 **M0b 短期不做**，「省掉一次重写」的收益兑现不了；而这里要的能力只是静态词条查表加十几条复数，用不上 i18next 的大半功能。桌面端「不引入 UI 框架级依赖」是历次 spec 的 Global Constraints 里明确守着的东西，为此开第一道口子不划算。

**实施中发现并修掉的一个安全缺陷**：sidecar 原本把 `system_prompt` 当**完整覆盖**（`prompt = system_prompt or default_prompt`）。语言指令一传，agent 的身份、授权边界、INV-39 敌对内容处理、skills、tools 会被整个替换掉——英文模式下每次运行都在裸奔。改为附加（`default_prompt + "\n\n" + system_prompt`），`tests/test_desktop_i18n_system_prompt.py` 挡回流。**这条缺陷与 i18n 无关，是 `system_prompt` 参数本身的问题，任何调用方传它都会中招。**

**由 i18n 引出的一条硬要求**：预设任务的中英两版必须命中 `plan_mode.RISK_KEYWORDS` 同一组关键词，否则同一个按钮在两种语言下审批行为不一致（INV-06）。`tests/test_desktop_i18n_risk_parity.py` 挡着。

**后续（2026-08-20）**：§K.1（connected 审批标题）与 §K.2（episodic 注入文案）均已收敛，**边界未放宽** ——
locale 始终没有传给 sidecar。K.2 尤其说明了这条边界立得住：那段中文的正解是统一成英文（系统提示词其余部分
本就全英文），而不是让 sidecar 按语言生成内容。

**关联**：`docs/superpowers/specs/2026-08-19-desktop-i18n-design.md`、`11-OPEN-QUESTIONS.md` §K（本决策的来源）、INV-06 / INV-38 / INV-39、DEC-027。
