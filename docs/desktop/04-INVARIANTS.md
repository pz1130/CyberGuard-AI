状态：定稿 · 2026-07-27

## 第一部分 · 设计哲学

不变量会有覆盖不到的新情况。**遇到文档没写的场景时，回到这五条原则推导，不要凭直觉猜。**

### 为什么安全 Agent 与编码 Agent 不同

参考项目（pi / codex / grok-build / claude-code-best / OpenClaw / Hermes）都是编码或通用助理场景。它们的设计不能直接照搬，因为四个前提是反的：

**动作可逆性的分布相反。** 编码 agent 绝大多数动作可逆（git 回滚、文件恢复）。安全动作大量不可逆——扫描包已经发出、进程已经杀掉、读取证据本身就改变了 atime。**编码 agent 可以"先做后审"，安全 agent 必须"先审后做"。**

**输入天然敌对。** 编码 agent 处理自己团队的代码库，基本可信。安全 agent 处理可疑样本、钓鱼附件解包、攻击者留下的日志与流量——**输入是攻击者写的**。prompt injection 对它们是理论风险，对我们是主要威胁模型。

**Agent 自身是高价值目标。** 一个能扫内网、跑 shell、持有域凭据的 agent，正是攻击者最想拿到的东西。

**产出要向第三方举证。** 编码 agent 只对开发者负责；安全产出要进合规审计，可能进法律程序。**证据链完整性优先于效率。**

### 五条原则

**P1 · 默认拒绝，能力靠显式授予。**
不是"除非被禁止否则可做"，而是"只能做被明确授予的"。

**P2 · 不可逆动作前置审批，审批对象是意图而非结果。**
审批"我打算扫 10.0.0.0/8"远比审批"我扫完了，这是结果"有意义。

**P3 · 能力变更是特权操作。**
agent 获得新工具、新技能、新权限，一律过人。agent 可以**提议**，人来批。

**P4 · 权限主体数量最小化。**
每多一个权限主体，安全审计成本上一个台阶。宁可牺牲灵活性。

**P5 · 所有降级路径必须显式且可见。**
**安全产品最怕静默降级**——以为在沙箱里，其实沙箱没启动。功能性失败可以 best-effort 降级；**安全边界失败必须响**。

### 凭据与密钥

**INV-01 · 凭据永不进沙箱。**〔P1〕
工具进隔离层，域凭据 / VPN 证书 / Provider API key / 节点密钥留宿主进程。
> 参照 pi 的 Gondolin 形态（工具与 shell 进 micro-VM，agent 进程留宿主）。反例是纯 Docker 方案，其文档明说 "Provider API keys enter the container"。
> **检查**：沙箱内进程的环境变量与可读路径不含任何密钥；专项用例。

**INV-02 · 一切节点侧凭据不落明文。**〔P1〕
覆盖**三类**：Gateway provisioning secret / `X-Api-Key`、节点级 Provider 凭据、未来的本地 MCP 凭据 slot。全部经 Electron `safeStorage`（底层 Keychain）存取，不写配置文件、不写 localStorage、不进日志。
> manifest 中只允许出现 `credential_ref`（如 `keychain://cyberguard/provider/...`）**这类引用，不得出现密钥本身**（09 §6.3）。
> 服务端 Provider 表中的原始 API Key **永不下发给节点**；节点级密钥**永不上传服务端**（DEC-017）。
> **检查**：构建产物与运行时目录全盘搜索无明文密钥；manifest 载荷 schema 断言无 `env_vars_encrypted` / auth token / provider key（09 §6.2）；日志脱敏用例。

### 完整性

**INV-03 · agent 不可修改自身策略与审计。**〔P1〕
`.cyberguard/`（节点密钥引用、下发策略、待上报审计缓冲）、`.git`、**原始证据目录**，在任何 `sandbox_mode` 下强制只读——包括位于可写根之内时。
> 被 prompt 注入的 agent 第一件事就是改策略文件和擦审计。参照 codex 在可写根内仍强制 `.git` / `.codex` / `.agents` 只读。
> **检查**：M2 专项用例，可写模式下写入这些路径必须失败。

**INV-04 · 原始证据只读。**〔P1〕
取证材料只读挂载，界面显示只读状态与 sha256。并行执行时各自独立临时工作目录，不共享可写区。
> **检查**：M5 专项用例；界面显示为验收项。

### 审批与职责分离

**INV-05 · 审批超时 = 拒绝。**〔P1 P5〕
不是"超时用默认值"。
> pi 的 Extension UI Protocol 是超时取默认值——安全产品必须反过来。
> **检查**：M4 专项用例。

**INV-06 · 职责分离审批按运行态分级，且降级必须标注。**〔P2〕

| 运行态 | 形态 |
|---|---|
| `connected` | 权限提升、跨主机动作、`autonomy_tier` L3 的批准权**在服务端**。节点界面不出现批准按钮，只做通知。 |
| `standalone` | 降级为**本地确认**。审计记录中必须标注 `approval_type: self`，界面显示"自批准"。 |

> HITL 的全部意义是批准者 ≠ 操作者。单机上只有一个人，这条**拓扑上无解**——所以只能诚实降级，不能假装。
> **绝不允许**：本地确认在审计里记成与职责分离审批相同的形态。将来合规审查看不出区别，就是给客户埋雷。
> **检查**：审计载荷断言 `approval_type` 字段必填且取值正确；connected 下界面走查无批准按钮；standalone 下界面必须显示"自批准"标识。

**INV-19 · 不可逆动作必须经 Plan Mode 前置审批。**〔P2〕
扫描、封禁、进程终止、配置变更等不可逆动作，不得依赖事后校验拦截。
> 现有 `_validation_node` 在结果里匹配 `critical` 关键词才要审批——那时动作早已发生。这是遗留设计，勿在节点侧复制。
> **检查**：M4 用例，标记为不可逆的工具在无批准计划时不得执行。

**INV-20 · 能力变更须人工批准。**〔P3〕
agent 获得新工具、新技能、新权限、新 MCP 服务器，一律经人批准。agent 可提议（附来源与证据），不可自行生效。
> 反例：Hermes 的自动学习闭环——任务完成后自动创建 skill 文件并立即可用。在安全产品里等于自我提权 + 持久化后门：一次成功的 prompt 注入可留下永久生效的技能。
> **检查**：技能池写入路径必经审批队列；专项用例。

### 权限主体与派发

**INV-21 · 跨 agent 派发必须做权限继承校验。**〔P4〕
目标 agent 的有效权限不得高于当前执行上下文。禁止通过派发实现提权；确需提权的走审批。
> 参照 OpenClaw 的 sandbox inheritance guard 及其三个连续沙箱逃逸公告（GHSA-p7gr-f84w-hqg5 等）：沙箱中的 session 通过跨 agent spawn 落到 `sandbox.mode="off"` 的 agent 下即可逃逸。
> **服务端现存同类问题**：`master.py::_parse_intent_node` 由 LLM 输出的 `task_plan` 直接携带 `agent_id`，`run_task` 拿它就执行，中间无权限比较。见 `03-ROADMAP.md` 遗留问题 6。
> **检查**：派发前断言 `target.effective_privilege <= context.effective_privilege`。

**INV-22 · 节点不做子 agent spawn。**〔P4〕
桌面节点是叶子执行者。并行止于**同一 agent 上下文内的工具并行**（`_run_loop` 现有的 `asyncio.gather` 分发），不产生新的权限主体、不新增上下文、审计链保持单条。
> 需要"专门的日志分析 agent"这类场景时，由**服务端派两个任务下来**，编排权始终在服务端。
> 见 DEC-012。
> **检查**：节点侧不存在 spawn/派发能力；代码走查。

**INV-23 · 服务端 fan-out 必须有闸。**〔P4〕
并发子任务上限、每 agent 活跃任务上限、嵌套深度上限、禁止不指定目标的派发。
> 参照 OpenClaw 的 `requireAgentId` 与三项上限配置。现有 `_sub_agent_executor_node` 的 `asyncio.gather` 无并发与深度限制。
> **检查**：配置项存在且默认值保守；压力用例。

### 上下文与压缩

**INV-33 · 压缩不得丢失授权边界。**〔P1〕
压缩摘要采用固定六段格式（Goal / **Constraints** / Progress / Key Decisions / Next Steps / Critical Context），其中 **Constraints 段必须包含当前生效的授权范围、目标白名单、沙箱模式、已批准的 plan 约束**。
> 这是安全 agent 与编码 agent 的关键差异点。分析师授权的是"只扫 10.1.2.0/24"，压缩后若该约束未进摘要，agent 在后续轮次就"忘了"边界——而它手上的工具真能扫出去。
> 固定格式的作用是**强迫模型覆盖每个维度**，而非挑有趣的写、漏掉用户要求（参照 pi 的六段设计）。现有 `_SUMMARY_PROMPT` 只有四段且无 Constraints；`internal_agent._maybe_compact` 是自由格式，连四段都没有。
> **检查**：压缩后授权范围仍在上下文中；越界扫描用例在压缩后仍被拦截。

**INV-34 · 压缩不得切断当前 turn。**〔P5〕
一次 run 中途触发压缩时，当前 turn（一次模型调用及其触发的全部工具执行）必须保持完整，不得被切开。
> pi 的做法是压缩发生在 **run 之间**；本系统 `_maybe_compact` 在 `_run_loop` 每轮开头调用，属 run 内压缩。模型正在执行一串工具调用时历史被换成摘要，会导致它"忘了"刚才在做什么。
> **检查**：长 run 压缩用例，断言当前 turn 的 assistant 消息与其全部 tool result 同侧。

### 运行态与档位

**INV-37 · standalone 必须自洽完整。**〔P1〕
任何核心工作流不得依赖服务端存在。断网、未配对、永不配对，产品都必须可用。
> 这是 DEC-022 的底线。standalone 一旦残废，"单机可用 + 可选连接"就退化成"服务端的卫星"。
> **检查**：全部核心用例在**无网络、无服务端配置**的环境下跑通（CI 独立 job）。

**INV-38 · 安全降级必须显式标注，不得伪装。**〔P5〕
本地确认不得记成职责分离审批（`approval_type: self`）；本地哈希链不得宣称等同 WORM；用户可自行关闭的开关不得呈现为安全边界。
> 这条统摄 INV-06、审计降级、standalone 模式授权三处。**给客户一个看起来更强的安全声明，比坦白降级危险得多**——它会让客户基于错误认知做合规判断。
> **检查**：审计载荷字段断言；产品文案与安全评审材料走查；界面标识用例。

**INV-39 · 敌对来源内容必须标记，且不得驱动特权动作。**〔P1〕

> ⚠️ **本条已于 DEC-027 重定义。** 原文是"上下文不得跨模式延续（切模式必须开新会话）"——那依赖双模式的强制隔离。产品定位改为**单兵全能**后，强制切模式是纯摩擦，但**要防的攻击链依然成立**，所以改为**内容级**的标记与降权，不再依赖会话边界。

进入上下文的内容按来源分级，**工具输出与外部数据默认为敌对来源**：

| 来源 | 可信度 |
|---|---|
| 用户直接输入 | 可信 |
| 内置技能、已批准技能 | 可信 |
| 本地文件 | 视 Trust Gate（INV-14） |
| **工具输出、MCP 返回、扫描结果、日志、样本内容** | **敌对，默认不可信** |

敌对来源的内容**不得**：

1. 改变已批准的约束（Plan 约束、授权范围、目标白名单）——与 INV-33 同源
2. 触发能力变更（创建技能、添加 MCP、提权申请的自动批准）——与 INV-20 同源
3. 在未标注的情况下作为结论依据——agent 基于敌对来源得出的判断，界面上须**可区分**并可溯源

**经验蒸馏同样受约束**：来源为敌对内容的经验，只保留结构化字段（工具序列、成功标记、耗时），**不保留自由文本 `outcome`**——自由文本才是注入载体。经验条目带 `source_trust` 标记。

> 这比原来的会话边界隔离**更强**：会话边界只是粗粒度近似，内容级标记不依赖用户是否切了模式。
> 攻击链本身没变——扫描结果里的注入内容影响后续判断建议。单兵场景下**更危险**，因为没有第二个人复核。
> **检查**：注入用例——在工具输出中埋入"忽略先前约束"类指令，断言（a）授权范围未被改变（b）未触发任何能力变更（c）受影响结论在界面上带来源标记；经验蒸馏用例断言敌对来源不产生自由文本条目。

**INV-40 · 审批界面的关键事实必须来自结构化字段。**〔P1 P2〕
影响范围、目标、请求方权限、风险等级——直接取自协议字段，**不得来自 LLM 生成的文本**。agent 可在旁给解读与建议，但须与事实**视觉可区分**，且每条结论可点开追溯到原始数据。
> 威胁模型随用户角色变化：分析师看到错误结论会自己核实，决策者是拿它做判断的。幻觉代价从"多跑一次工具"变成"批准了不该批的动作"。
> **检查**：审批视图渲染路径的静态检查，断言关键字段不经过模型输出；溯源链路用例。

**INV-41 · connected 只能收紧；脱管由服务端判定，节点侧留痕。**〔P1 P5〕
服务端策略与本地策略取**更严者**，服务端不得放宽超过用户本地设定。连接不得要求上传全量会话（L2 明确不做，见 DEC-023）。
用户可随时断开回到 standalone——**阻止不了，不要试**——但脱管必须可见。

**脱管的判定责任在服务端，不在节点。** 节点侧做三件事：界面显著显示"脱管中"并列出失效的限制、转变写入本地审计链、**能上报时上报**。服务端侧按**心跳超时**判定脱管，不依赖节点主动通知。
> 早期版本写的是"断开前上报并留痕"——**这在物理断网时做不到**：用户拔网线或直接关机，根本没有上报的机会。依赖节点自觉上报的机制，对最需要发现的那种脱管恰恰失效。
> 不假装能锁住用户，但让脱管可见。
> **检查**：策略合并函数的取严用例；**拔网线/强制关机场景下服务端仍能在超时窗口内判定脱管**；节点侧本地审计留痕用例。

### 交付与更新

**INV-42 · 更新通道必须验签且防降级。**〔P1〕
更新包独立签名并强制验签（公证之外的第二道）；更新源 HTTPS 且证书固定；**不得被诱导安装存在已知漏洞的旧版本**；更新动作进审计。
> 客户终端上装着持有域凭据、能跑扫描与 shell 的应用。更新源被劫持 = 向所有客户终端投递任意代码的能力，**目标恰好是安全团队的机器**。这是供应链攻击的教科书入口。
> **检查**：篡改更新包用例必须被拒；降级安装用例必须被拒；中间人用例必须被拒。

### 通信与暴露面

**INV-07 · 节点不监听任何端口。**〔P1〕
壳 ↔ sidecar 走 stdin/stdout JSONL；节点 ↔ 服务端仅出向 HTTPS。控制指令搭 heartbeat 响应回传。
> **检查**：`lsof -i` / 集成测试断言无监听 socket。

**INV-08 · Electron 安全配置不可放宽。**〔P1〕
`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`，仅经 `contextBridge` 暴露白名单方法。
> **检查**：启动时断言 + CI 静态检查。

**INV-09 · 不做 LAN 自动发现与节点间 P2P。**〔P1 P4〕
企业网内的跨机器自动发现与任务交换是横向移动通道。拓扑保持星型：节点只与服务端通信。
> **检查**：依赖清单中不得出现 mDNS / Bonjour / UDP 广播 / P2P 类库（CI 阻断）；集成测试断言节点仅有指向服务端的出向连接。

### 数据边界

**INV-10 · 全量对话与证据不出本机。**〔P1〕
上报服务端的只有：审计事件、结果摘要、artifact 哈希、`policy_events`。
> **检查**：`report` 载荷 schema 校验用例。

**INV-11 · 本地经验库归本地，上传须显式逐条确认。**〔P1 P4〕

> ⚠️ **本条已于 DEC-022 反转。** 原文为"节点不建本地向量库，经验留服务端"——那是 standalone-first 之前的结论，现已作废。

`standalone` **必须建本地经验库**（否则没有经验积累，产品价值大打折扣）。`connected` 后本地库仍在（个人经验），叠加服务端共享库（组织经验），两层分工不混。

**本地经验上传服务端必须：可选、逐条显式确认、且经脱敏。** 不得做成自动同步——本地经验里可能含客户敏感信息与调查细节。

> 跨人共享仍是 connected 的核心价值之一（DEC-023），但它不能成为 standalone 缺失经验能力的理由。
> **检查**：无确认的自动上传路径不存在（专项用例）；上传载荷经脱敏管线；本地库在断网时可用。

**INV-12 · 报告工件不得出网。**〔P1〕
不生成公开可访问 URL。artifact 带 sha256 与保留期，上报服务端存证。
> 反例：claude-code-best 的 artifacts 传公网带过期 URL——对取证报告是灾难。
> **检查**：artifact 落盘与上报路径的专项用例，断言不产生外部 URL；节点出向连接白名单只含服务端地址（与 INV-09 同一套断言）。

### 控制流

**INV-13 · 用户可控输入不得直接驱动控制流。**〔P1〕
分支判断走结构化字段或先过 guardrail，不用关键词匹配。
> 服务端有两处**遗留违例，勿模仿、待单独修复**：`master.py::_parse_intent_node` 用 `"discuss"` 等关键词触发 group chat；`_validation_node` 用 `"critical"` 等关键词判定高风险。两者都绕过了五层 prompt-injection guardrail。
> **检查**：控制流分支点的静态检查——分支条件不得直接消费 `user_input` / 工具输出的原始字符串；对抗用例（在正常请求中嵌入 `discuss` / `critical` 等触发词）不得改变执行路径。

**INV-14 · 不可信目录的本地资源默认不加载。**〔P1〕
本地上下文文件、技能、设置须先通过 trust gate。全局资源无条件加载，项目本地的必须显式信任。
> 节点分析的目录（可疑样本、取证介质拷贝、钓鱼附件解包）**天然是攻击者可控的**。放一个构造好的指令文件即可直通 agent，且绕过服务端 guardrail——拼进 system prompt 发生在节点侧。参照 pi 的 project trust（`trust.json`，默认 ask）。
> **检查**：M5 专项用例，含 prompt 注入样本。

**INV-24 · system prompt 中须含不可协商的禁令。**〔P1〕
下发的 system prompt 固定包含若干条显式 "never do X"，作为 prompt injection 的最后一道防线。该段不可被会话内容覆盖。
> 参照 OpenClaw `SOUL.md` 的边界声明设计。
> **检查**：prompt 组装单测断言禁令段存在且位置固定。

### 降级与可见性

**INV-25 · 安全边界的失败不得静默降级。**〔P5〕
沙箱初始化失败、策略加载失败、审计缓冲写入失败、trust 判定失败——**必须中止或显著告警，不得 `except: pass` 放过**。
> 功能性降级（经验召回失败、搜索失败、OCR 失败）可以 best-effort no-op，这是好设计；安全边界失败必须反过来。**两者不可混用同一套错误处理模式。**
> **检查**：安全路径的异常处理专项走查；沙箱初始化失败注入用例必须导致任务不启动。

**INV-16 · 沙箱不可用时只允许只读档位。**〔P1 P5〕
`sandbox_impl: none` 时，**本地工具执行能力不得启用**——只允许只读档位（不注入本地 `ExecOperations`）。状态栏须显著告警。
> 降级路径从第一天就存在且被测试，否则会在客户现场变成"关掉沙箱就能用"的口子。
> **standalone 下由节点自身在会话创建时强制**（没有服务端派单可拦）；`connected` 下服务端另按 `node_caps` 收紧。
> **检查**：`sandbox_impl` 伪造为 `none` 的用例中，完整作业档位不可选、本地 `ExecOperations` 不被注入。

**INV-26 · 禁止扩展与技能热重载。**〔P3〕
任何能力变更（新工具 / 技能 / 扩展 / MCP 服务器）必须经审批后**重新加载**才生效，不得改完立即生效。
> 反例：pi 的扩展系统支持热重载，修改立即生效不需重启会话。对单人工具是便利，对安全产品是**绕过审批的能力变更通道**。
> **检查**：加载路径只存在于启动与显式 reload；专项用例。

**INV-27 · 内建最小工具集不可被下发内容覆盖。**〔P1〕
节点有一组固定内建的核心工具，manifest 下发的工具**不得同名覆盖**它们，冲突时内建优先并告警。
> 理由是可验证性：内建工具的沙箱行为可以静态验证并写进安全评审材料，下发工具不行。
> 现有 manifest 处理中，MCP 与工具池重名时 MCP 胜出并 warn——同一模式，但内建集必须位于两者之上。
> **检查**：命名冲突用例。

### 工具执行管线

> **策略与审计是两套机制，不得合并。** 参照 pi：管线钩子有干预能力（可阻断、可改写），事件系统是纯观察（不可否决、不可修改）。混为一谈会导致要么审计能篡改结果，要么策略无法拦截。

**INV-28 · 所有工具执行必经策略管线，管线钩子可否决。**〔P1 P5〕
统一管线：`prepare_arguments` → `validate_arguments` → **`before_tool_call`（可阻断）** → `execute` → **`after_tool_call`（可改写 / 脱敏 / 打标）**。不得在旁路直接执行工具。
> `pii_handling_policy` 的脱敏落点就是 `after_tool_call`——现在这个字段在调用链上层层透传却没有统一执行点。
> 沙箱决策、Plan Mode 拦截、kill switch、权限继承校验（INV-21）全部挂 `before_tool_call`。
> **收益不只是整洁**：可以静态验证"每条路径都过了策略检查"，这对安全评审是硬通货；散落在 `_dispatch` / `tool_executor` / `run_task` 的检查无法证明这一点。
> **检查**：静态分析用例，断言不存在绕过管线的工具调用点。

**INV-29 · 审计走事件，事件不可否决且必须被 await。**〔P5〕
审计与可观测性订阅事件流（agent / turn / message / tool_execution 四层，各自 start → update → end）。订阅者是纯消费者：**不能否决、不能修改**事件。
emit **必须 await**，按订阅顺序逐一等待完成——**审计写入完成才继续下一步**。监听器抛异常向上传播，不得静默吞掉。
> fire-and-forget 的审计对安全产品是个洞：任务已经继续推进，审计却可能从未落盘。高频的 `tool_execution_update` 可批量 await 以控制开销。
> **检查**：审计写入失败必须中止当前 turn（与 INV-25 一致）；专项用例。

**INV-30 · 工具参数必须经 schema 校验后才进入执行。**〔P1〕
模型输出的参数在 `validate_arguments` 阶段按工具声明的 `input_schema` 做运行时校验，校验失败返回结构化错误，**不执行**。
> 现状是硬伤：`_dispatch` 用 `json.loads(...)` 加裸 except，失败则 `args = {}`，随后直接传给工具——而工具池的工具是用 `command_template` 拼命令的。**manifest 已下发 `input_schema`，却只用来告诉模型，没用来把关。**
> **检查**：畸形参数注入用例，含类型不符、缺必填、超长、注入字符。

**INV-35 · 节点不得接收或执行任意 shell 命令字符串。**〔P1〕
manifest 下发的本地工具必须是**结构化命令**：可执行文件绝对路径 + 固定参数 + 经 schema 校验的变量参数，并通过本地白名单检查。**不得下发需要 shell 解释的命令模板。**
> 这条封死了 `command_template` 字符串拼接这条注入路径——参数校验（INV-30）只能保证类型，保证不了"参数里带 `;` 和反引号"。两条一起才完整。
> 需要 shell 语义的动作走 `governed` 服务端代执行（INV-18）。
> 来源：09 §6.1。
> **检查**：manifest schema 断言无自由命令字符串字段；注入用例（参数含 `;` / `` ` `` / `$()` / 换行）不得产生额外进程。

**INV-36 · 审计缓冲不得静默丢弃。**〔P5〕
report 超时须持久化到本地 append-only audit buffer；buffer 有明确上限，**达到上限时停止派发新的高风险任务并显著告警**；恢复联网后按序上报，服务端按 `report_id` 幂等去重。
> 节点状态栏须常显待上报数量与暂停状态。审计积压等于审计链断裂，不能靠丢弃来"恢复正常"。
> 来源：09 §10。与 INV-25 同源——安全边界的失败必须响。
> **检查**：断网 + buffer 打满用例，断言新高风险任务被拒且界面告警；重复上报用例断言服务端去重。

**INV-31 · 有副作用的工具默认串行。**〔P1〕
工具声明 `execution_mode: sequential | parallel`。**一票否决**：一批 tool_calls 中任一声明 sequential，整批串行执行。结果消息按原调用顺序发出。
> 现状 `_run_loop` 无条件 `asyncio.gather` 全部并行。安全场景下同时写同一取证工作区、同时对同一目标发起扫描、任何有副作用的动作都不能并行。
> **默认值必须是 sequential**，并行是显式选择——默认危险是错误的默认。
> **检查**：并发写同一工作区用例必须被串行化。

**INV-32 · 工具错误必须结构化，不得靠字符串前缀识别。**〔P1 P5〕
工具失败返回带 `is_error: true` 的结构化结果，不抛异常穿透循环。错误信息要具体到模型可自我纠正。
> 现状 `_dispatch` 返回 `f"ERROR: ..."` 字符串，`tool_call_end` 用 `result_str.startswith(("ERROR", "LOOP_DETECTED", "BUDGET_EXHAUSTED"))` 判断——**这是字符串前缀嗅探**，工具输出里恰好有一行以 ERROR 开头就会误判成失败。
> 两层策略（参照 pi）：工具层主动识别已知错误类型并附上下文；框架层兜底捕获未知异常。
> **检查**：输出内容含 "ERROR" 前缀但实际成功的用例，不得被判为失败。

### 架构

**INV-15 · 沙箱能力必须是平台无关的声明式描述。**
上层只见 `sandbox_mode` + `writable_roots` + `network_access`。Seatbelt / `.sbpl` 的假设不得泄漏出 macOS 实现模块。
> 这条是二期加平台成本可控的唯一保障。
> **检查**：代码走查 + `packages/agent-core` 的 import lint。

**INV-17 · `agent-core` 不认识基础设施。**
包内禁止 import `sqlalchemy` / `redis` / `celery` / `fastapi` / `app.*`。
> **检查**：lint 规则强制，CI 阻断。

**INV-18 · 两级工具执行的边界不得模糊。**〔P1〕
`governed = true` 的工具只能走 `/gateway/execute-tool` 由服务端代执行，节点不得本地执行。
> manifest 已通过 `command_template=None if agent.governed` 在协议层保证——不要在节点侧另开旁路。
> **检查**：M3 专项用例。
