# 桌面端 MCP 连接器生命周期设计

状态：设计 · 2026-07-29 · 阻塞 M1

**为什么先做这个**：`advisory` 与 `operator` 两种模式都依赖它，且与 advisory 的功能范围（尚未定，见 `docs/desktop/11-OPEN-QUESTIONS.md` §A）解耦。M1 就需要雏形。

---

## 1. 现状与差异

服务端现有 `app/services/mcp_executor.py` 是个**薄客户端**：STDIO MCP 托管在隔离的 `tool-runner` 容器里，本模块解密 per-server env（tool-runner 没有加密密钥）后，把 start/stop/status/call/discovery 通过 HTTP 代理过去。HTTP transport 的 MCP 则在进程内直连。

桌面端**没有 tool-runner 容器**，sidecar 直接 spawn。所以需要第二套实现。

**这正好落在 Operations 抽象上**（DEC-015）：MCP 的 spawn 与调用应当在端口之后，服务端注入"代理到 tool-runner"的实现，桌面端注入"本地 spawn"的实现。上层 agent 循环两边一致。

---

## 2. 决策一：由 Python sidecar spawn，不由 Electron main

**决策**：MCP 子进程由 Python sidecar 直接 spawn 与管理。

**备选**：Electron main（Node）spawn，再把 stdio 转发给 sidecar。

**理由**：MCP 客户端协议逻辑属于 agent-core 的调用链，放 sidecar 里链路最短。走 Electron 会变成 `sidecar → Electron → MCP` 的双跳 stdio 转发，既增加延迟又增加一处可能丢帧的边界。

**代价**：MCP server 是 Electron 的**孙进程**，清理需要显式处理——见下一节。

---

## 3. 决策二：孤儿进程必须显式治理

**这是本设计最容易出事的地方，也是唯一一处出错会留下持有凭据的残留进程的地方。**

macOS 没有 Linux 的 `PR_SET_PDEATHSIG`，父进程死亡不会自动通知子进程。三层防护缺一不可：

**① 进程组**：sidecar 启动时 `setsid()` 建立新进程组；所有 MCP 子进程落在同一组。sidecar 正常退出时 `killpg` 整组。

**② 看门狗**：sidecar 定期检查 `os.getppid()`。返回 `1` 说明 Electron 已死、自己被 init 收养 → **立即清理全部 MCP 子进程并自杀**。轮询间隔建议 2 秒。

**③ Electron 侧兜底**：`before-quit` / `will-quit` 中向 sidecar 发 SIGTERM，设定超时（建议 5 秒）后 SIGKILL。异常退出路径（崩溃、强制退出）依赖 ①②。

**安全含义**：残留的 MCP server 可能在内存里持有从 Keychain 取出的凭据，而且没有任何进程在管它。这不是资源泄漏问题，是**凭据暴露窗口**。

**验收**：`kill -9` Electron 主进程后，`ps` 中不得残留任何 MCP 子进程（专项用例）。

---

## 4. 决策三：凭据注入与 slot 隔离

**注入方式**：沿用环境变量（MCP 生态的事实标准，改用 stdin 首帧需要 server 端配合，不现实）。

**约束**：

- **只注入该 server 自己的 slot**。每个 MCP server 对应一个 Keychain 条目（`keychain://cyberguard/mcp/<server-id>`），不得跨 server 读取（DEC-018 修正版）。
- 凭据**只在内存中经手**，不写入任何文件、不进日志、不进会话记录。
- 进程退出后不做任何持久化残留。

> macOS 上 `ps -E` 查看他人进程环境变量需要 root，同用户其他进程看不到——相对安全，但凭据在子进程整个生命周期驻留内存这一点无法消除，因此更要靠 §3 的孤儿治理兜底。

**验收**：为 server A 配置的凭据，在 server B 的进程环境中不可见（专项用例）。

---

## 5. 决策四：沙箱化按"是否需要凭据"分两类

**这里与 INV-01（凭据永不进沙箱）有一处真实张力**，必须先解开：MCP server 需要凭据去调外部 API，但 INV-01 禁止凭据进沙箱。

解法是认清 INV-01 的原意——**不要让"能跑任意代码的工具沙箱"里出现凭据**。据此分两类：

| 类别 | 例子 | 隔离手段 |
|---|---|---|
| **无凭据 MCP** | 本地文件解析、格式转换、离线分析 | **进工具沙箱**（Seatbelt），无网络，`writable_roots` 受限 |
| **有凭据 MCP** | 连 SIEM / 云平台 / 工单系统 | **不进工具沙箱**，改用**网络出向白名单**——只能连它声明的 endpoint |

有凭据的 MCP server 本质是一个受信任的连接器，它的隔离维度应当是网络而非文件系统。声明的 endpoint 写在 server 配置里，运行时强制。

**验收**：有凭据 MCP 连接声明之外的地址必须失败（专项用例）。

---

## 6. 失败处理：区分功能性降级与安全信号

INV-25 要求安全边界失败必须响、功能性失败可 best-effort。MCP 的失败要落到正确的一侧：

| 情况 | 归类 | 处理 |
|---|---|---|
| MCP server 启动失败 / 崩溃 / 超时 | 功能性降级 | 该数据源标记不可用，界面显示，**不中断任务** |
| 单次调用返回错误 | 功能性降级 | 结构化 `is_error` 返回给模型自行处置（INV-32） |
| **凭据 MCP 连续认证失败** | **安全信号** | **告警，不静默重试**——可能是凭据泄漏或已被吊销 |
| 返回输出超限 | 安全信号 | 截断 + 告警（与 INV-36 同源），防止撑爆上下文或磁盘 |
| 连接了声明之外的地址 | 安全信号 | 阻断 + 告警 + 进审计 |

**重启策略**：指数退避，最大重试次数可配；连续失败达阈值后标记不可用并在状态栏显著提示，不再无限重试。

---

## 7. standalone 下的信任建立

connected 时 MCP 由 manifest 下发，服务端已经批准过（含 `binary_sha256`）。

**standalone 下没有下发**，用户自己添加。按 INV-20 的 standalone 形态，**用户自己添加即自己批准**——但必须是**知情同意**，不是走过场。

添加时界面必须明确列出这个进程将获得什么：

- 以当前用户身份运行（拥有你的全部文件权限）
- 将访问的网络地址（声明的 endpoint 白名单）
- 将拿到哪个凭据 slot
- 是否进沙箱（按 §5 分类自动判定并显示）

**不要**用一句"添加 MCP 服务器？[确定]"糊弄过去。这是产品对用户诚实的地方，也是 INV-38（降级必须显式）的应用。

---

## 8. 资源与超时

- **单次调用超时**：沿用 `MCPServer.timeout_seconds`（默认 30s），manifest 下发时可覆盖。
- **输出大小上限**：超限截断并标记，走 §6 的安全信号路径。
- **进程级限制**：内存与文件描述符上限，防止单个失控 server 拖垮整个应用。
- **启动策略**：**懒加载**——首次调用到该 server 时才 spawn，可配置预热。全量启动在接十几个数据源时会显著拖慢启动。

---

## 9. 分阶段落地

| 阶段 | 范围 |
|---|---|
| **M1** | spawn / 停止 / 崩溃可见 + **§3 孤儿治理三层防护** + 单次调用超时。凭据不做（M1 是 mock 环境） |
| **M2** | §5 无凭据类 MCP 的沙箱化（随 Seatbelt 一起落地） |
| **M3** | §4 凭据 slot、§5 有凭据类的网络白名单、§6 失败分类与告警、§7 知情同意界面、§8 懒加载 |
| **M6** | manifest 下发的 MCP 与本地添加的合并策略、`binary_sha256` 校验 |

**M1 的孤儿治理不能推迟。** 它不是优化项——没有它，开发期每次崩溃都会积累残留进程，而到了 M3 有凭据时，残留进程就变成凭据暴露窗口。**先建立正确的进程模型，比事后补救便宜得多。**

---

## 10. 三条补充决策

**健康检查用轻量 `tools/list`，且只在必要时。** MCP 规范没有通用的 ping。方案：进程存活由 OS 层面判断（`waitpid` / 退出码）为主；只有在**一次调用失败之后**才用 `tools/list` 探一次以区分"进程死了"和"这个工具坏了"。**不做周期性主动探测**——那是纯成本，且对空闲连接毫无意义。

**HTTP transport MCP 单独处理，不套用本文的生命周期模型。** 它不需要 spawn、没有子进程、没有孤儿问题，生命周期就是 HTTP 客户端的连接管理。桌面端支持它，但走独立路径：凭据仍进 Keychain slot、endpoint 白名单仍强制、失败分类（§6）仍适用，**但 §2/§3 的 spawn 与孤儿治理完全不涉及**。不要为了"统一"把两者硬塞进一个抽象。

**同名冲突按优先级，与技能一致**：内置 > 组织下发 > 本地添加。高优先级胜出**并告警**，不静默覆盖。见 `2026-07-29-skill-system-design.md` §2。
