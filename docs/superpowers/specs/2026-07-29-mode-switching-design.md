# 桌面端模式切换机制设计

状态：设计 · 2026-07-29 · 阻塞 M1（骨架）/ M3（完整）

`advisory`（决策）与 `operator`（作业）的授权、隔离与切换。

> ## ⚠️ 已按 DEC-027 重新定位
>
> 产品定位改为**单兵全能工具**后，双模式的前提（"CISO 与工程师是两批人，能力需分开授权"）不再成立。同一个人既看态势也下场查，强制切模式新建会话是**纯摩擦**。
>
> **现在的形态**：模式降级为**会话创建时的能力档位**（"只读咨询 / 完整作业"），**默认完整作业**。
>
> **仍然有效的部分**：§1 的"档位是会话不可变属性"（消除中间态与竞态）、§2 的"靠依赖注入而非条件判断"（类型层面就没有本地 `ExecOperations`）、§7 的"advisory 不等于无害"。
>
> **已被取代的部分**：§3 的服务端授权集合（connected 降为按需）、§4 的强制上下文隔离——**改由 INV-39 的内容级敌对来源标记承担，不再依赖会话边界**。那比会话隔离更强：不管用户切没切档位，工具输出永远是敌对来源。

---

## 1. 核心决策：模式是会话的不可变属性

**决策**：模式在会话创建时确定，**终生不变**。所谓"切换模式"，底层语义是**以另一模式新建会话**。

**备选**：模式作为应用级可变状态，当前会话跟着切。

**理由**：

1. **INV-39 自动成立**。上下文不跨模式延续这条约束，如果模式可变，就要处理"切换瞬间已有上下文怎么办"——清空？保留？部分保留？每个答案都是漏洞面。设成不可变属性，这个问题从存在性上消失。
2. **不存在"切换中"的中间态**。没有中间态就没有 TOCTOU 类的竞态：不会出现"检查时是 advisory，执行时已变成 operator"。
3. **审计天然清晰**。每条会话记录自带模式，不需要在时间线上追溯"这一步当时是什么模式"。

**UI 上仍可呈现为模式切换器**，但点击的实际效果是新建会话并切过去。旧会话保留在列表里。

---

## 2. 模式决定什么

| 维度 | `advisory` | `operator` |
|---|---|---|
| **Operations 注入** | **不注入本地 `ExecOperations`** | 注入（受沙箱约束） |
| 可用工具集 | MCP + 检索 + 生成 | 上述 + 本地工具 |
| 沙箱要求 | 无（不执行本地工具） | 全套 Seatbelt（M2 判据通过才解锁） |
| system prompt | 决策/聚合导向 + 对应禁令段 | 作业/取证导向 + 对应禁令段 |
| UI 布局 | 工作项队列 三栏 | 会话树 三栏 |

**关键手法：靠依赖注入而非条件判断。**

`advisory` 会话的 agent-core 实例**根本没有本地 `ExecOperations`**。这不是"检查模式后拒绝执行"，是**类型层面就没有这个能力**。

这与 INV-18（两级工具执行边界不得模糊）用的是同一个手法，收益也一样：从"靠代码走查保证"升级为"靠类型系统保证"，不需要担心哪里漏了一个分支判断。

> 与 INV-16 的关系：`sandbox_impl: none` 的机器只允许接 read-only 任务。advisory 本就不执行本地工具，因此**在无沙箱能力的机器上 advisory 仍然可用**——这也是 advisory 不受 M2 阻塞的技术依据。

## 3. 授权来源

| 运行态 | 可用模式集来自 |
|---|---|
| `standalone` | **用户自选**。单机上用户有 root，不存在能约束他的机制 |
| `connected` | 服务端按 RBAC 角色与授权策略下发，界面只能在集合内选 |

授权集合存于 `.cyberguard/policy.json`（对 agent 强制只读，INV-03）。

**standalone 下必须诚实**（INV-38）：界面上的模式选择器**不得呈现为安全控制**。它是一个偏好设置，不是权限门。措辞与视觉都要与 connected 下的"已授权模式"区分开。

**connected 下取更严者**（INV-41）：服务端可以收窄可用模式集（例如只授权 advisory），不能扩大到用户本地未启用的范围。

## 4. 上下文隔离 —— 以及一个新发现的漏洞

INV-39 要求 advisory 与 operator 不共享会话上下文。§1 的不可变属性设计已经保证了这一点。

**但会话上下文不是唯一的跨模式通道。** 以下东西是跨会话共享的：

经验库、技能、知识库、个人偏好。

**这里有个漏洞**：`operator` 会话跑扫描时，结果里可能含攻击者构造的内容（恶意服务 banner、被污染的日志）。这些内容经蒸馏进入**经验库**后，`advisory` 会话召回时会把它带进上下文——**绕过了 INV-39 的会话隔离，直接打到审批决策上**。

这正是 INV-39 想堵的那条攻击链，只是换了一条路径。

**处理方式**：

1. 经验条目必须带 `source_trust` 标记（`trusted` / `hostile`）——**按内容来源而非模式**，见 INV-39 重定义版。
2. 召回 `hostile` 来源的经验时，**只取结构化字段**（工具序列、成功标记、耗时），**不取自由文本的 `outcome`**——自由文本才是注入载体。
3. 技能同理：`operator` 场景产生的技能草稿进入 advisory 可用集之前，须经人工审阅（本来就要，见 INV-20）。
4. 知识库与个人偏好由用户主动录入，风险较低，但录入自不可信来源的材料时仍走 Trust Gate（INV-14）。

**验收**：注入用例——在 operator 会话的工具输出中埋入指令文本，断言其不出现在后续 advisory 会话的上下文中（含经由经验召回的路径）。

## 5. 并存与切换

**允许多模式会话并存。** operator 会话在后台跑扫描、用户同时在 advisory 看态势，是合理场景，不应禁止。

**切换（=新建）时不中断已有会话**。旧会话继续按自己的模式运行，在会话列表中可见，状态栏显示各模式的活跃会话数。

**不做的**：不提供"把当前会话转成另一模式"的操作。需要时新建，历史留在原会话。

---

## 6. 脱管状态

`connected → standalone`（断开）后，服务端下发的授权集合失效，回到 standalone 的"用户自选"。

**这意味着服务端的模式限制在断开后形同虚设——这是事实，不要试图掩盖。** 用户断开就是脱管，脱管后他在自己的机器上有 root。

正确处理是三条：

1. **界面显著显示"当前为脱管状态"**，并列出因脱管而失效的限制。
2. **转变本身进审计**（本地审计链必记；能上报时上报）。
3. **服务端侧按心跳超时判定脱管**——不依赖节点主动上报断开（节点被拔网线或关机时根本没有上报机会，见 `docs/desktop/11-OPEN-QUESTIONS.md` §D 中记录的已知错误）。

这与 INV-38 一致：**不假装能锁住用户，但让脱管可见。**

---

## 7. advisory 不等于无害

容易被误读的一点：advisory 不执行**本地**工具，但它通过 MCP 对外部系统做的动作**同样有副作用**——关工单、给告警打标、改云配置、触发 playbook。

因此：

- **advisory 同样需要 Plan Mode 式的执行前确认**（INV-19），只是审批对象是 MCP 侧的动作而非本地命令。
- 有副作用的 MCP 工具同样适用"默认串行"（INV-31）。
- 声明 endpoint 白名单同样强制（见 MCP 连接器设计 §5）。

**不要因为"不执行本地工具"就给 advisory 放宽策略管线。** 五步管线两种模式都必经（INV-28）。

---

## 8. 审计

会话创建时记录：模式、授权来源（`standalone-self` / `connected-granted`）、当时的授权集合快照、运行态。

运行态变更（connected ↔ standalone）单独记录，含失效的限制清单。

---

## 9. 分阶段

| 阶段 | 范围 |
|---|---|
| **M1** | 模式作为会话不可变属性的**骨架**；Operations 按模式注入（advisory 不注入本地 `ExecOperations`）；会话列表按模式区分 |
| **M2** | operator 模式与沙箱能力绑定；`sandbox_impl: none` 时 advisory 仍可用 |
| **M3** | 授权集合读取与界面呈现、§4 的经验库跨模式污染防护、审计字段、脱管状态显示 |
| **M6** | connected 授权下发、策略取更严者、脱管判定 |

**M1 的关键不是 UI，是把"模式 = 会话不可变属性 + Operations 按模式注入"这个模型立住。** 模型对了，后面每一层加上去都是自然的；模型错了（做成可变应用状态），M3 会推倒重来。

## 10. 待定

- **默认模式**：首次启动进哪个？倾向 `advisory`（更安全，且不需要沙箱就绪）。
- **快捷切换的粒度**：是否允许"以相同上下文摘要新建另一模式会话"（把上一会话的结论作为初始输入，而非完整上下文）。这在"advisory 发现问题 → 转 operator 深挖"的场景很自然，但**摘要本身也可能是注入载体**，需要单独评估。
- **模式与 LLM Profile 的关系**：advisory 处理的是组织敏感材料，是否应默认限制在 `local_only` Profile，禁用 `approved_remote`？
