# 桌面端本地敏感数据保护设计

状态：设计 · 2026-07-29 · 阻塞 M3

**为什么优先级上升**：原按分析师场景评估（证据摘录、内网拓扑）。`advisory` 定位确立后，CISO 机器上会有**未披露漏洞、进行中的事件细节、董事会材料、监管沟通**——敏感度高一个量级，且这台机器本身成为高价值目标。

---

## 1. 先说清楚防谁、防不了谁

**不诚实的威胁模型会做出安全剧场**，而安全剧场直接违反 INV-38。所以先划边界。

macOS 上 FileVault 已提供全盘加密。应用层再加一层，**防得住的**：

- 机器丢失或被盗，**且 FileVault 未开启**
- 备份泄漏（Time Machine、iCloud、企业备份系统）
- 同机其他非特权用户账户
- 目录被误分享 / 误同步到云盘
- **卸载后的残留**

**防不住的**（不要宣称能防）：

- root 用户
- 已解锁机器上的攻击者
- 内存取证
- 拥有完全磁盘访问权限的其他应用（EDR 本身就有）

**结论**：应用层加密的真实价值集中在**备份泄漏与残留清理**，不是防本机攻击者。产品文案必须按这个边界写。

---

## 2. 数据分级

| 层 | 内容 | 敏感度 | 保护重点 |
|---|---|---|---|
| **凭据** | 节点密钥、Provider 凭据、MCP slot | 极高 | Keychain（INV-02，已有方案） |
| **会话正文** | 对话、工具输出、证据摘录 | **极高** | 机密性 + 可销毁 |
| **artifacts** | 取证报告、董事会材料 | **极高** | 机密性 + 不出网（INV-12） |
| **审计链** | 操作事件、哈希链 | 高 | **完整性优先**于机密性 |
| **经验库** | 蒸馏后的打法（含目标网段、系统名） | 中 | 机密性 |
| **技能 / 知识库** | 用户录入 | 视内容 | 机密性 |
| **策略 / 配置** | `policy.json`、manifest 缓存 | 低 | **完整性**（INV-03） |
| **临时文件** | 工具中间产物、MCP 输出 | **常被忽略但可能最高** | 生命周期管理 |

---

## 3. 决策一：FileVault 检测优先于自建加密

**决策**：启动时检测 FileVault 状态，未开启则**显著告警**并引导开启。这条的实际防护收益高于任何应用层加密，而成本接近零。

应用层加密作为**补充**（针对备份泄漏与残留），不是替代。

**不要**在 FileVault 未开的机器上用应用层加密制造"已加密"的安全感——那正是 INV-38 禁止的伪装。界面应明确：「全盘加密未开启，本机数据在设备丢失时可被读取」。

---

## 4. 决策二：两级密钥 + crypto-shredding

**SSD 上传统的覆写删除是无效的**（wear leveling 会保留旧块）。唯一可靠的"安全删除"是**加密后丢弃密钥**。

**两级密钥结构**：

| 密钥 | 作用域 | 生命周期 |
|---|---|---|
| **索引密钥** | 会话元数据索引（标题、时间、分支关系） | 长期，随应用 |
| **会话数据密钥** | 每个会话正文一把 | 随会话；**删除会话 = 删除该密钥** |

两级都存 Keychain。

**为什么会话正文要 per-session 密钥**：这样"删除某次调查的全部痕迹"是一个原子且可靠的操作——丢弃密钥即可，不必依赖文件系统的覆写语义。

**元数据索引为什么也要加密**：会话标题本身就可能是敏感信息（"某某公司数据泄露事件调查"）。搜索时整体解密到内存——桌面端会话量级在数百，全量解密可接受。

**artifacts 同样按 per-artifact 密钥**处理，理由相同。

---

## 5. 决策三：审计与正文分离，保留期不同

**张力**：审计需要**长期保留**（合规、复盘、举证）；会话正文希望**尽早过期**（减少暴露窗口）。

**解法**：两者本就应该分离。

- **审计事件**是结构化摘要——动作、时间、参数摘要（`args_digest`）、结果状态、哈希。**不含正文**。长期保留。
- **会话正文**可设独立的、较短的保留期。过期后 crypto-shred，审计链完整性不受影响。

这与 INV-10（上报服务端时只给审计事件、摘要、哈希）是同一个思路，**在本地同样适用**：正文和证据是最敏感的部分，也是最不需要长期保留的部分。

**默认保留期**建议：会话正文 90 天可配；审计链不设自动过期（用户可显式导出后清理）。

> 与 INV-03 的关系：审计缓冲与哈希链对 agent 强制只读，与本节的保留策略不冲突——保留策略由用户在界面上操作，不经 agent。

---

## 6. 备份排除

敏感目录必须**排除出备份**，否则数据会流进 Time Machine 或 iCloud，绕过本地的一切保护。

需要排除：`sessions/`、`episodic/`、`.cyberguard/audit-buffer/`、临时工作目录。

**不排除**：`skills/`（用户自己写的技能有备份价值）、配置。

> 注意这与"审计需长期保留"的张力：审计链被排除出备份意味着机器损坏就丢失。解法是提供**显式的加密导出**功能（用户主动导出到自己选择的位置），而不是依赖系统备份。

---

## 7. 临时文件与崩溃转储 —— 最容易漏的两处

**临时文件**：工具执行中间产物、MCP server 输出、解压的证据。这些常常包含**最敏感的原始内容**，却因为"是临时的"而没人管生命周期。

要求：统一落在应用管理的临时目录内（不用系统 `/tmp`）、随会话结束清理、随应用退出兜底清理、纳入备份排除。

> PyInstaller 选 onedir 而非 onefile（DEC-008）在这里有额外收益：onefile 每次启动解压到临时目录，等于持续在临时区留下可执行内容。

**崩溃转储**：Electron 默认收集 crash dump，**其中可能含进程内存内容**——而进程内存里有凭据和会话正文。

要求：**默认禁用崩溃上报**；如需诊断，转储本地保留、加密、用户显式同意后才能导出。这条不要等出事再补。

**日志**：INV-02 已要求脱敏，此处具体化——日志不落敏感字段、设保留上限、位置纳入清理与备份排除。

---

## 8. 卸载清理

客户会卸载。本应用留下的东西比普通 app 多，且**取证材料索引留在卸载后的机器上是合规问题**。

| 项 | 处理 |
|---|---|
| Keychain 条目（节点密钥、Provider、MCP slot、数据密钥） | 卸载流程删除。**删掉数据密钥即完成 crypto-shred** |
| `~/Library/Application Support/CyberGuard/` | 删除 |
| 临时目录 | 删除 |
| TCC 完全磁盘访问授权 | **无法程序化撤销**——提示用户到系统设置手动移除 |
| 用户生成的 artifacts（用户自选位置） | **不擅自删除**，列出清单让用户自行处理 |

必须提供**文档化的卸载流程**并说明哪些会被清、哪些需手动。见 M7。

---

## 9. 分阶段

| 阶段 | 范围 |
|---|---|
| **M1** | 临时目录统一管理与退出清理；**禁用崩溃上报**；日志脱敏与保留上限 |
| **M3** | FileVault 检测与告警、两级密钥与会话正文加密、crypto-shredding、备份排除、审计/正文保留期分离 |
| **M7** | 卸载流程与文档、加密导出功能 |

**M1 的三项都很小但不能推迟**：临时文件和崩溃转储一旦形成习惯路径，后面再收就要翻遍所有写文件的地方。**先建立"敏感数据只落在受管位置"的习惯，比事后收拢便宜得多**——与 MCP 孤儿治理同理。

---

## 10. 待定

- ~~加密算法与密钥派生选型~~ → **已定**：使用系统提供的 CryptoKit / `Security.framework`，**不自带实现**。理由是减少安全审计面——客户的安全团队审自研加密的成本远高于审"用了系统 API"。
- **会话正文保留期的默认值**：90 天是拍的，需要按客户实际复盘周期调整。
- **connected 下的保留期是否由服务端策略收紧**：属 L1 范畴（DEC-023），但会与本地用户设置冲突，取更严者的语义在"保留期"上是"更短"还是"更长"？——**合规通常要求更长，安全要求更短，这条方向不明确，需单独讨论。**
- ~~导出加密格式~~ → **已定**：用**标准格式**（age 优先，GPG 次之）。理由是客户能用既有工具解密——自定义格式意味着"要读自己的数据必须装我们的软件"，对取证材料的长期留存是不可接受的锁定。引入依赖的代价可接受。
