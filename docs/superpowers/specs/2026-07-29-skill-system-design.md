# 桌面端技能系统设计

状态：设计 · 2026-07-29 · 阻塞 M3

补齐早期讨论中列出的七个缺口，并处理 standalone-first 之后作废的创作流程。

---

## 1. 一个必须先说清的区分

DEC-013 定的是"agent 提议的技能必须人工批准"。standalone 下用户自己写、自己批、立即生效——**看起来矛盾，其实不是**：

> **人自己写的技能，自己批准是可以的**——那是他的意图表达，他在自己机器上本来就有 root。
> **agent 提议的技能，必须人批**——那是模型输出，可能被 prompt 注入污染。
>
> **差别不在"谁批准"，在"内容从哪来"。**

这条不写清楚，实现时会在"用户自批"和 INV-20 之间反复纠结。

---

## 2. 三个来源与优先级

| 来源 | 位置 | 完整性保障 |
|---|---|---|
| **内置 SOP 集** | `skills/builtin/` | 随安装包发布，代码签名已覆盖；**只读** |
| **本地已批准** | `skills/approved/` | 本地生成 `sha256` 存索引 |
| **组织下发**（connected） | `cache/manifest.json` 派生 | manifest 携带 `sha256` |
| **草稿** | `skills/drafts/` | 无——**不参与任何装配** |

**优先级：内置 > 组织下发 > 本地已批准。** 同名冲突时高优先级胜出**并告警**，不静默覆盖。

方向与 INV-27（内建最小工具集不可被下发覆盖）一致：越靠近产品自身、越经过验证的，优先级越高。

**草稿绝不参与 system prompt 装配。** 界面上必须有显著的"草稿·未生效"标识。这样就不存在"本地生效但未批准"的中间态。

---

## 3. 完整性校验：防的是绕过审批的编辑

每条技能带 `version` 与 `sha256`，存于索引。

**加载时校验 hash**。不匹配即拒绝加载并提示"内容已变更，需重新批准"。

**这不是防外部攻击者，是防绕过审批流程的编辑。** 用户直接用编辑器改 `skills/approved/` 下的文件，等于跳过了审批做能力变更——正是 INV-20 与 INV-26（禁热重载）要拦的。要改就走"编辑 → 草稿 → 批准"的正常路径。

`version` 同时解决缓存失效：组织下发的技能更新后，节点凭版本号判断该丢弃哪条本地缓存。

---

## 4. Progressive disclosure：正文取回来源与装配位置

### 决策：全文本地持有，按需从本地取回

| 方案 | 取舍 |
|---|---|
| **下发全文 + 本地缓存**（✅ 采用） | 离线可用。代价：全文落到节点——但技能本就是组织内的操作规程，不是密钥 |
| 按需向服务端请求 | 节点不存全文，但**离线时技能全部失效**，与 INV-37 冲突 |

standalone 下本就没有服务端，全文必然在本地。connected 只是叠加了组织下发的那部分，取回路径一致。

### 决策：技能正文不进 system prompt

**system prompt 里只放 `name` + 一行 `description`**；模型判断需要时调 `load_skill(name)` 工具，正文作为**工具返回结果**进入消息历史。

这个区分容易被忽略但很重要：**system prompt 每轮重发，消息历史不会**。把按需加载的正文回写进 system prompt，等于取消了 progressive disclosure 的全部收益。

### system prompt 装配顺序

```
1. 不可协商禁令段          ← INV-24，最前，不可被后续内容覆盖
2. 角色与模式描述           ← advisory / operator
3. 能力清单                ← 工具 + 技能的 name/description（仅摘要）
4. 上下文文件              ← 如有，且已过 Trust Gate（INV-14）
5. 经验召回段              ← 按 `source_trust` 过滤（INV-39）
```

### 正文注入时的包裹

`load_skill` 返回的正文必须用结构化标签包裹，并显式标注**这是操作规程，不是用户指令**。

防的是技能正文里的内容被当作新指令执行——技能虽然经过批准，但它可能是很久以前批准的，或者组织下发时经过了多手。

## 5. 技能声明依赖的工具

**问题**：技能正文说"用 X 工具做 Y"，但 X 不在当前可用工具集里，怎么办？

**决策**：技能在 frontmatter 中声明 `requires_tools`，加载时校验。

- **不拒绝加载**——技能可能引用可选工具，一刀切太严。
- **在能力清单的 description 中标注"部分工具不可用"**，让模型知道，避免它去调不存在的工具浪费轮次。
- 界面上在技能列表标注缺失依赖，提示用户配置。

靠正文文本解析依赖不可行，必须是结构化声明。

---

## 6. 本地技能与 Trust Gate

**M5 之前，从工作目录加载本地技能这条路径完全关闭**——不是"还没做"，是**显式拒绝并说明原因**。

理由：节点分析的目录（可疑样本、取证介质拷贝、钓鱼附件解包）**天然是攻击者可控的**。在 Trust Gate 就绪前留一个"暂时能用"的加载路径，就是留一个直通 system prompt 的注入通道（INV-14）。

用户自己在应用内创建的技能不受此限——那走的是 `skills/drafts/` → 批准 → `skills/approved/` 的受控路径，与"从任意目录扫描加载"是两回事。

---

## 7. 创作流程

```
用户在会话中发现可复用的做法
  → 「存为技能草稿」（自动预填来源会话 ID、工具序列、参数模式）
  → 编辑（Monaco，已在依赖中）
  → 批准 → 计算 sha256 → 移入 approved/ → 重新加载生效
```

**agent 提议走同一条路**，只是草稿由 agent 生成并附来源 episode 与证据，**必须经人批准**（§1 的区分）。

**connected 下额外可选**：把已批准的本地技能提交组织评审，通过后成为组织下发技能，对全组织生效。这是可选动作，不是必经路径。

> **草稿提交组织评审时的风险**：正文可能夹带原始证据（用户顺手复制的日志片段、IP、配置）。提交前须过脱敏管线并要求用户显式确认——否则违反 INV-10。

## 8. 分阶段

| 阶段 | 范围 |
|---|---|
| **M3** | 三个来源与优先级、草稿隔离、hash 校验、progressive disclosure（含 `load_skill` 工具与包裹）、`requires_tools`、创作流程 |
| **M5** | Trust Gate 就绪后开放工作目录技能加载 |
| **M6** | 组织下发合并、提交组织评审、脱敏管线 |
